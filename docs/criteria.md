# Условия и критерии кейса

Источник — презентация кейса «Новостная аналитика для принятия бизнес-решений» (Альфа-Банк × Changellenge, 19 слайдов).
Номера критериев и ограничений — как в презентации. Колонка «Чем закрываем» — наш ответ; держать в актуальном состоянии.

## Задача (слайд 6)

1. Проанализировать данные о компании и/или группе: отрасль, положение в ней и долю рынка, виды деятельности, масштаб и другие признаки, влияющие на значимость новостей.
2. Механизм персонализированного **отбора и ранжирования** новостей под бизнес-контекст компании.
3. **Персонализированная интерпретация** значимых событий на основе признаков из п. 1 с учётом аналитики Альфа-Банка.
4. Пользовательский сценарий и интерфейс **в интернет-банке Альфа-Бизнеса**: факты, аналитика и интерпретация — понятно и последовательно.
5. **Парсер** новостей из внешних источников и аналитических материалов Альфа-Банка: классификация и выделение ключевой информации.

## Требования к агентной логике (слайд 7)

Не однократная генерация, а многошаговый процесс. Логику реализует команда сама (один агент с инструментами или обоснованная мультиагентная система).

| Требование | Что значит | Чем закрываем |
|---|---|---|
| Планирование | Система определяет нужные данные и источники и формирует последовательность шагов | Шаг `plan` агента, виден в трассе |
| Работа с инструментами | Профиль клиента, новости, аналитика банка, поиск/RAG, другие инструменты | `get_company_profile`, `search_bank_analytics`, `search_news`, `get_counterparties` |
| Контекст | Результаты предыдущих шагов используются в следующих | Единый журнал шагов агента; итог опирается на результаты инструментов |
| Самопроверка и адаптация | Оценка полноты, непротиворечивости, обоснованности; повторный поиск при необходимости | Валидатор карточки без LLM + проверка моделью; при ошибках — шаг `research` и правка |

## Формат сдачи (слайд 8)

- [ ] Код в GitHub с историей коммитов; **commit hash или тег на момент дедлайна** (коммиты после дедлайна не учитываются). Приватный репозиторий — доступ аккаунту жюри **`alfa-hack-2026`**.
- [ ] `README.md`: назначение, архитектура, требования к окружению, запуск, конфигурация и переменные окружения, компоненты, **пошаговый сценарий проверки**.
- [ ] Docker-конфигурация и единый воспроизводимый способ запуска.
- [ ] Lock-файлы или иная фиксация версий языка и зависимостей.
- [ ] `THIRD_PARTY_NOTICES`: сторонние компоненты, модели, датасеты, сервисы и **смоделированные интеграции**.
- [ ] Синтетические тестовые данные и, если нужно, тестовые учётные записи для сквозного сценария.
- [ ] Желательно: архитектурная схема, описание API / OpenAPI, модель данных, тестовые сценарии.
- [ ] Рекомендуется заранее развернуть решение на бесплатном внешнем сервере.
- На демонстрации показать, **как меняется лента под клиента** и что в новостях. Нужен **работающий прототип, с которым можно взаимодействовать**, а не заранее подготовленные экраны.

## Критерии успеха (слайды 9–10)

| № | Критерий | Чем закрываем |
|---|---|---|
| 01 | Сервис определяет бизнес-контекст клиента по данным и отбирает события, значимые для конкретного клиента, с учётом релевантных признаков | Профили из 3 CSV (`docs/data.md`); отбор пар «компания × событие» по правилам на признаках; `matched[]` в карточке |
| 02 | В интерпретации используются аналитика и экспертная позиция Альфа-Банка из материалов кейса; пользователь понимает, где позиция банка, а где вывод AI | Поиск по 9 документам банка; `p: bank` с источником; цветовая разметка факт / банк / ИИ |
| 03 | Корректно отбирает, объединяет и суммаризирует внешние и внутренние материалы, сохраняет связь выводов с первоисточниками, минимизирует фактологические ошибки | Дедупликация событий; `src` у каждого факта; сверка чисел с текстом источника в валидаторе |
| 04 | Устойчивое качество на **ранее не показанных новостях**; не зависит от подготовленных сценариев | Живой сбор из RSS / t.me; разбор произвольной новости вживую; никаких захардкоженных событий |
| 05 | Полный сценарий: от входа в сервис до понятной интерпретации с рисками, возможностями и (если обосновано) следующим действием | Главная → виджет → карточка → разбор → кнопка действия |
| 06 | Содержательная интерпретация: последствия, риски, возможности с учётом **нескольких факторов**, не пересказ и не очевидное следствие одной новости | Вывод строится из профиля (продукты, ВЭД, отрасли контрагентов) + позиции банка + связанных событий |
| 07 | Масштабирование на новые отрасли, типы клиентов и источники данных; подход к техническому сопровождению | Источники — конфиг; профиль строится из любых CSV той же схемы; раздел README про сопровождение |
| 08 | На **главном экране** интернет-приложения Альфа-Бизнеса — заметная и постоянно доступная точка входа | Виджет «Важное для вашего бизнеса» + пункт меню с бейджем новых |
| 09 | Интерфейс взаимодействия с аналитикой: **уточняющий вопрос**, **данные в другом разрезе**, **переход к первоисточнику** | Чат по карточке с графиком/таблицей; ссылки на источники |
| 10 | Агентная логика: сам формирует и выполняет шаги, обращается к источникам и инструментам, **корректирует процесс** при недостаточных или противоречивых данных | Свой цикл с инструментами; повторный поиск после самопроверки |
| 11 | Трассируемость: восстановимы источники, признаки компании, повлиявшие на вывод, результаты существенных промежуточных этапов | Трасса шагов в карточке; журнал вызовов инструментов; `basis.features` |
| 12 | Метрики и процесс регулярного мониторинга качества контента, персонализации и AI-компонентов с учётом обратной связи пользователей и экспертов | «Полезно / Не про нас» → метрики; доля карточек, прошедших валидатор; стоимость; экспертная разметка мини-набора |

## Ограничения (слайды 11–12)

| № | Ограничение | Чем закрываем |
|---|---|---|
| 01 | Не обычная лента и не пересказ новостей ИИ; ценность — глубокая интерпретация с учётом контекста клиента | Двухуровневая карточка: событие + вывод под компанию и роль |
| 02 | Аналитика и мнение Альфа-Банка — **заметная часть ценности и влияют на выводы** | Блок «Как оценивает банк» + `p: bank` в коротком слое карточки |
| 03 | Учитывать особенности конкретной компании, а не только отраслевые тренды | Продукты, ВЭД, контрагенты, группа, масштаб — в правилах отбора и в промпте |
| 04 | Только разрешённые LLM; общий ключ с дневным лимитом **500 ₽** | Белый список моделей в клиенте; кеш ответов; правила отбора без LLM; учёт стоимости в трассе |
| 05 | Безопасность AI-компонентов: разграничение прав, защита чувствительных данных, контроль и **журналирование обращений к инструментам**, ограничения на небезопасные действия. Для прототипа — описать и показать место в архитектуре | Инструменты только на чтение и по белому списку; журнал вызовов; агент видит профиль только выбранной компании; описать в README |
| 06 | Корректная работа с **неполными, неоднозначными и зашумлёнными** данными | Плашка качества данных, `basis.coverage`, пометка устаревшей аналитики, «данные расходятся» |

Пример из кейса (ограничение 01): новость о сохранении ставки 14% 11.09.2026. Недостаточно — пересказ решения ЦБ.
Хорошо — «период быстрого удешевления кредитов приостановлен, деньги остаются дорогими, финансовая нагрузка на компании
с заёмным финансированием не снизится». Карточка `i-rate-auto` в моках построена ровно по этому примеру.

## Пространство решений (слайд 13)

Разрешено: любые подходы к бизнес-контексту (классификация, анализ признаков, графовые модели), RAG при сохранении связи
с источниками, любой интерфейс, один или несколько агентов. Рекомендован обмен между AI-компонентами в **JSON по схеме**,
отделяющей подтверждённую информацию, аналитику банка и выводы модели. Допустима **нативная реклама продуктов банка**.

## Структура интерпретации (слайд 14)

Шесть вопросов, на которые отвечает карточка, — это наши шесть блоков:
что произошло (`what`) · почему важно этой компании (`why`) · какие последствия возможны (`risks`, `opportunities`) ·
какие действия релевантны (`actions`) · как оценивает банк (`bank`) · на чём основан вывод (`basis`, `sources`).

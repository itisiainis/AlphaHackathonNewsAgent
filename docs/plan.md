## 2. Что известно (ограничения и решения)

Жёсткие ограничения — в `CONTRIBUTING.md`: только разрешённые модели в рантайме, свой агентный цикл, 500 ₽/день,
работа на новых новостях, сдача через Docker одной командой с README, lock-файлами и THIRD_PARTY_NOTICES.

Решения, уже принятые командой (`docs/product.md`): основной интерфейс — сайт, Telegram — опционально;
сначала вывод, потом детали; 3 события на главной; у каждого утверждения есть происхождение и источник;
аналитика банка старше 12 месяцев помечается устаревшей и в выводе не используется.

## 4. Что берём из Telegram-бота

Бот читает Telegram-каналы и RSS, дешёвой моделью оценивает посты пачками, раскладывает по рубрикам и собирает дайджест.
Это ровно первая половина нашего конвейера: сбор новостей и первичный отбор.

| Файл бота | Что делает | Решение |
|---|---|---|
| `webcollector.py` | Чтение публичных каналов через `t.me/s/…` без ключей | **Берём как есть.** Есть тесты (`tests/test_webcollector.py`) |
| `feeds.py` | Поиск RSS на сайте и чтение лент | **Берём как есть** — ЦБ, Интерфакс, РБК, Минфин, Росстат |
| `collector.py` (`Post`, `normalize_ref`) | Модель поста и чтение через Telethon | Берём `Post`. Telethon **не берём**: он работает через личный аккаунт и файл сессии — в сдаваемом решении это риск безопасности |
| `documents.py` | Текст из PDF через `pypdf` | **Берём** для загрузки аналитики банка |
| `pipeline.py` | Пачечная оценка постов (20 штук за запрос), важность 0–10, рубрики, `geo`, `category` | **Берём схему, переписываем промпты.** Рубрики пользователя заменяются темами из `roles.weights` (ставка, долг, курс, ликвидность, отрасль, спрос, контрагенты) |
| `pipeline.build_digest` | Сборка HTML-дайджеста | Не нужен для сайта. Пригодится, только если делаем Telegram-канал (Could) |
| `llm.py`, `config.py` | Клиент коммерческих API моделей | **Не берём.** Нарушает ограничение кейса. Пишем свой клиент к разрешённым моделям |
| `bot.py`, `db.py`, `digest.py`, `deploy/` | Команды бота, SQLite, расписание, systemd | Только для опционального Telegram-канала |

Что учесть при переносе:
- В `README` и `.env.example` бота по умолчанию стоят коммерческие модели не из списка кейса. В репозиторий хакатона эти строки попасть не должны.
- `RESTORE.md` содержит IP сервера и вход по root — в репозиторий не коммитим.
- В `RESTORE.md` написано, что архив снят «до добавления админ-функций», но в коде архива уже есть `/allow`, `/revoke`, `/users` и таблица `users`. Описание архива и его содержимое не совпадают — для нас это не критично, но архиву как «точной копии» доверять не стоит.
- Тесты бота в этой сессии не запускались — прогнать после переноса.

## 5. Что берём из проекта по кейсу Авито

Само решение Авито нам не подходит: там разбор намеренно сделан без LLM, у нас LLM — ядро продукта. Берём метод работы:

1. **Документ анализа кейса** по той же структуре: задание → границы MVP → пользователи → FR/NFR с номерами →
   приоритизация (основное / обеспечивающее / дополнительное, порядок отказа) → прецеденты → архитектура → модули.
   У нас его роль частично выполняет `docs/product.md`; не хватает пронумерованных требований и привязки к критериям (Q1).
2. **Контракт в первый день.** У Авито это `openapi.yaml` + JSON Schema сценария. У нас — JSON Schema карточки и OpenAPI для 5–6 эндпоинтов.
3. **Модули с непересекающимися файлами** и общие точки стыковки (у нас: схема карточки, профиль компании, формат документа аналитики).
4. **CI на каждый PR**, шаблон PR с чек-листом, `AGENTS.md` с соглашениями.
5. **README как отчёт для жюри**: быстрый старт одной командой, таблица «что работает сейчас», ключевые решения,
   границы MVP, распределение ответственности, раздел «Использование ИИ».
6. **Ошибка, которую не повторяем:** в Авито заявлено требование покрытия 60% (MNT5), а в README итог 35,5%.
   Обещаем жюри только то, что реально проверено и измерено.

Принцип «демонстрация не должна упасть», из-за которого Авито отказались от LLM, у нас решается иначе:
карточки для демо предрасчитаны и закешированы, вживую считается только новая новость (критерий 05).

### 6.1. Двухуровневая карточка — главный способ уложиться в бюджет

Событие одно для всех компаний, вывод — свой у каждой. Поэтому генерация делится на два уровня:

| Уровень | Что генерируется | Сколько раз | Модель |
|---|---|---|---|
| Событие | `title`, `blocks.what`, `blocks.bank`, `sources`, темы | 1 раз на событие | Сильная (DeepSeek-V4.1-Flash или Qwen3.6 — выбрать по замеру) |
| Компания × событие | `takeaway{cfo,ceo,treasurer}`, `key_points`, `why`, `risks`, `opportunities`, `actions`, `basis`, `matched` | Только для пар, прошедших отбор | Сильная, короткий промпт |

Отбор пар «компания × событие» — **без LLM**, правилами по профилю: темы события ↔ продукты банка
(кредит/лизинг → ставка, долг), ВЭД и страны → курс, ОКВЭД компании и её контрагентов → отрасль и спрос.
Сила связи считается как в `docs/product.md`: `score = сила влияния × 10 + сумма весов тем роли`.
Правила дают и поле `matched[]`, и объяснимость отбора.

### 6.2. Модели по задачам

| Задача | Модель (стартовый выбор) | Примечание |
|---|---|---|
| Оценка важности, темы, дубли — пачками по 20 | Gemma 4 | Схема из `pipeline.score_posts` бота |
| Черновик карточки, чат | DeepSeek-V4.1-Flash / Qwen3.6 | Сравнить на мини-наборе из раздела 7, этап 3 |
| Самопроверка черновика | Другая модель, не та, что писала черновик (GLM-5.3-Flash или Kimi-K2.6) | Независимая проверка сильнее аргументом для жюри |
| Графики и таблицы из PDF аналитики | Qwen3-VL | Только если в аналитике есть графики без текстового слоя |

Выбор моделей — гипотеза. Решаем по замеру качества и цены на мини-наборе, не по ощущениям.

### 6.3. Поиск по аналитике банка

Если embedding-модели нет среди разрешённых (Q4) — BM25 по фрагментам документов плюс фильтры по дате и теме.
Для 10–100 документов этого достаточно, и это объяснимо в трассе.
Фильтр `max_age` уже заложен в моках (`search_bank_analytics(..., max_age=90д)`).
Документ старше 12 месяцев возвращается с `stale: true` и в вывод не идёт (как в карточке `i-steel`).

### 6.4. Валидатор карточки — детерминированная проверка честности

Отдельная функция без LLM. Её отчёт попадает в трассу шагом «Самопроверка»:

1. Карточка соответствует JSON Schema (поля из `CONTRIBUTING.md`).
2. У каждого утверждения есть `p ∈ {fact, bank, ai}`.
3. `fact` и `bank` обязаны иметь `src`, индекс существует; у `bank` источник имеет `kind: bank`.
4. Числа из утверждений `fact`/`bank` находятся в тексте указанного источника — иначе утверждение переписывается или помечается `ai`.
5. Источник `bank` старше 12 месяцев → `stale: true`, в `takeaway` и `key_points` не используется.
6. При неполных данных в `basis.coverage` выводится доля известного потока из профиля.

Пункты 3–5 — то, что отличает нас от «пересказа новостей»: происхождение проверяется кодом, а не обещанием модели.

### 6.5. API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/companies` | Список компаний для переключателя |
| `GET` | `/api/roles` | Роли и веса тем |
| `GET` | `/api/feed?company=&role=` | Лента карточек, отсортированная под роль |
| `GET` | `/api/cards/{id}?company=` | Карточка с трассой |
| `POST` | `/api/analyze` | Новая новость (текст или URL) → карточка; шаги агента идут потоком (SSE) |
| `POST` | `/api/cards/{id}/chat` | Вопрос по карточке |
| `POST` | `/api/cards/{id}/feedback` | «Полезно / Не про нас» |

Стек: Python, FastAPI (асинхронный, как сборщики бота; Pydantic-модели = проверка контракта; OpenAPI генерируется сам), SQLite для кеша.
Фронт — текущий шаблон, отдаётся тем же сервисом. Один контейнер, `docker compose up`.

## 9. Риски и вопросы жюри

| Вопрос / риск | Ответ |
|---|---|
| «Это пересказ новостей» | Двухуровневая карточка: вывод строится из профиля (продукты, ВЭД, отрасли контрагентов), а не из текста новости. Показываем одну новость у двух ролей и двух компаний |

| «Агент или цепочка промптов?» | Свой цикл: модель сама выбирает инструменты, самопроверка может запустить повторный поиск — видно в трассе |
| Модельный API недоступен на защите | Демо-карточки в кеше; живой разбор — отдельный шаг с честной пометкой |
